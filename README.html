01谁在跑：四个执行体

这是最容易带着 Node 直觉读错的地方。Node 里「处理一张图」是 require('sharp'), 一个进程、一次调用、一个返回值。这里不是:同一时刻有 四个执行体,它们之间靠 管道、文件和 HTTP 说话。

关键前提

libvips 是外部二进制,不是链接进来的库。 Rust 侧没有 libvips-sys, 它是 std::process::Command 起了一个 vips.exe,读它的 stdout,看它的退出码 （src-tauri/src/vips.rs 文件头）。 代价是要自己解析文本输出;换来的是 macOS 用 brew 的、Windows 用随包捆绑的, Rust 侧不必处理两套构建系统。

给 Node 背景的对照表

这里的东西Node / 浏览器里对应什么差别在哪
#[tauri::command] + invoke('x') 一个 POST /x 路由 不走网络栈,是进程内 IPC;参数/返回值靠 serde 自动 JSON 化
tauri::generate_handler![…] Express 的 app.use() 路由表 漏注册 = 前端 invoke 直接 reject,没有 404 日志
app.emit("tile-progress", payload) WebSocket / SSE 推送 广播式,前端 listen() 订阅;发早了没人收（事件会丢）
自定义协议 bigimgpin:// 一个只服务缓存目录的静态文件服务器 图片字节不走 IPC —— 见 §5
async command + spawn_blocking 重活丢给 worker_threads,别堵事件循环 同步命令会跑在 UI 主线程,几分钟的切片直接冻界面
#[serde(rename_all = "camelCase")] DTO 层的字段名转换 Rust tile_size ↔ TS tileSize,改一边必须改另一边

02瓦片金字塔是什么

一张 41041 × 49841 的图约 20.5 亿像素,按 8 位 RGB 展开是 6 GB —— 还没算解码器的中间缓冲。所以大图不能「打开」,只能按视野分块、按需加载。 金字塔就是这件事的数据结构:同一张图预先降采样出一串越来越小的版本,每一级再切成固定大小的方块。 放大看细节时取最深那级的几块,缩到全图时取最浅那级的一块。

它落在磁盘上长这样

vips dzsave 产出的是标准 DZI（Deep Zoom Image）—— 微软定的格式, OpenSeadragon 原生会读。下面这份是本机缓存里真实的一份（源图 3000 × 2000）:

反直觉的地方

目录号 0 是最小的一级,号越大越清晰。 12/ 才是全分辨率,0/ 只有 1 个像素。 OpenSeadragon 那边的 level 用的是同一套编号（getLevelScale(level) = 1 / 2^(maxLevel - level), level = maxLevel 时 scale 就是 1),所以前端拿到的 level 号可以直接当目录名拼 URL —— 见 §5 的 getTileUrl。

亲手切一遍

下面这个金字塔是按仓库里那段公式现算的（vips.rs::expected_tile_count: 每一级尺寸是上一级的一半、向上取整,一直降到 1 × 1）。改宽高或瓦片尺寸,看它怎么变:

每一行是一个目录（磁盘顺序,从 0/ 开始）。方块 = 一张瓦片,按真实比例排布。 最后一行就是全分辨率那层,打开图时看到的就是它的局部。

三个数字里的取舍

瓦片为什么是 1024,而不是 DZI 惯用的 256

瓦片越大,压缩算法在单张瓦片内能匹配到的重复图案越多,总体积越小 —— 实测 2048 比 512 省约 40%。 但解码后的内存是平方增长的:1024 瓦片解码后一张 4 MB。 OpenSeadragon 默认缓存 200 张且不按内存预算,默认值会吃掉 800 MB。 所以最终定 1024（commands.rs 顶部）,并把 OSD 缓存压到 80 张: 1080p 视口、1024 瓦片时实际只用约 9 张,加倍留余量足够。

为什么默认 WebP 无损,不是 JPEG 也不是 PNG

  • 比 PNG 小约 35%,而逐像素相减最大差值为 0（真无损）。
  • 不用 JPEG: 目标图是边缘锐利的版图类图像,JPEG 会在每条边产生振铃伪影, 而那可能被当成真实结构读出来。对一个用来「看结构」的工具,这条不能接受。
  • PNG 用默认压缩档:实测 compression=9 只省 8%,却慢数倍。

有测试守着 extension() 不许出现方括号（extensions_have_no_option_brackets）—— 它拼进 URL,一旦带上选项,前端请求的就是一个不存在的文件名。

逐跳代码

1用户点「打开图片」App.vue:690

按钮在 ToolBar.vue,事件冒到 App。App 只做编排:调 api、接结果、把错误放进横幅。

2invoke —— 唯一的跨进程出口src/api/tauri.ts

组件从不直接 import invoke。 所有命令与事件都封在这一个文件里, 于是「前端能叫后端做什么」是一份可以一眼读完的清单,参数名写错也只会在这一个地方错。

命名约定

invoke 的第二个参数里,键名必须和 Rust 函数的参数名对上（path、params）, 而返回对象里的字段走 serde 的 camelCase,所以 Rust 写 tile_size、TS 收 tileSize。 Rust 的 Result::Err 在 JS 侧表现为 Promise reject —— 所以 vipsInfo() 成功就代表 vips 可用,返回类型里没有 available 字段。

3Rust 弹系统对话框commands.rs:117

放在 Rust 侧的唯一原因:这里拿到的直接是绝对路径,前端不用去猜、也不用处理路径编码。

async fn 不只是风格问题 —— 同步命令跑在 UI 主线程,一个阻塞几百毫秒的对话框就够界面卡一下。

4loadPath：一次「打开」的全部前端动作App.vue:713

这个函数是前端这一侧的主干。注意中间那段刻意的 await 顺序,它有硬性理由（见 §7 的「半新半旧」）。

顺带一提

LAST_IMAGE_KEY 存的是源图路径而不是瓦片目录:瓦片是缓存、随时会被清掉, 路径是「我想看的是哪张图」,两者生命周期不一样。启动时若命中缓存,这次打开是秒开的。

5prepare_image：先算缓存键，再说切不切commands.rs:139

命令一进来就干三件事:解析参数 → 读文件元信息（大小 + mtime）→ 算 cache_key。 这个 key 就是目录名,切片参数也进 hash,理由见 §4。

两个细节
  • 命中缓存这条路径仍然要起一次 vipsheader（probe_image）: 前端需要真实的宽高去构造 DziTileSource,而这个信息只存在源图里。 好在这只是读文件头、不解码图像,几十毫秒。
  • Rust 的 map_err(|e| …) 把 io::Error 换成人类可读的中文串 —— 这个串会一路原样出现在界面横幅里。Result<T, String> 是 Tauri 命令的常见形态。
6探图：不解码图像，只读文件头vips.rs:119 · vips::probe_image

这一跳就是 vips::probe_image（src-tauri/src/vips.rs:119）: 起一次 vipsheader -a <图>,把它的输出按「key: value 一行一个」读出来。 解析时要求行以 key 开头,不能只是包含 —— 第一行是路径,而路径里完全可能含 "width"。

这里的 format 字段（uchar / ushort / float…） 后面导出裁剪图时会用到:它决定用什么容器存 —— 见 §8。

7真正跑起来的那条命令vips.rs:297

spawn_dzsave 用参数拼出的就是这条命令行（默认参数下,out_base 不含扩展名）:

每个启动都过 vips_command()

它做两件平台相关的修饰:设 VIPS_PROGRESS=1（让 vips 把百分比打到 stdout）, 以及在 Windows 上加 CREATE_NO_WINDOW —— vips.exe 是 console 程序, 从 GUI 进程启动会闪黑框。

8切片期间：为什么必须是 spawn_blockingcommands.rs:207

child.wait() 会阻塞到切片结束 —— 几分钟。所以整段包在 tauri::async_runtime::spawn_blocking 里,不占死异步运行时的工作线程; 而命令本身是 async,不占 UI 主线程。两层都要,少一层就是界面冻住。

「取消」按钮走的是另一条命令 cancel_slicing:它把存下来的 pid 拿出来杀掉。 Unix 用 SIGKILL（vips 可能忽略 TERM 继续跑完）,Windows 用 taskkill /PID … /F /T。

9进度：两条来源并行，取较大值vips.rs:328 · App.vue:146

一条是 vips 自己报的百分比,一条是数已经落盘的瓦片文件。为什么要两条:vips 的进度输出是多线程的, 并不平滑,某段时间可能一动不动,用户会以为卡死。

兜底那条是另一个线程,每 400 ms 递归数一次 image_files/ 里的文件数,除以预期的总张数 （expected_tile_count,就是 §2 那个交互图在算的公式）。

事件的时序陷阱

Tauri 的 emit 是广播,且不排队:监听器还没注册时发出的事件直接消失。 所以启动自检 vips_status 有两条来源 —— 事件,加上前端主动调一次 vips_info 兜底（App.vue 挂载末尾）。这个项目的做法是: 凡是「必须知道」的状态,都要有一个可主动拉取的命令。

10返回值：PreparedImage 这份契约commands.rs:388 · types.ts:2

Rust 侧所有的「到这一步为止,前端需要知道的一切」都压进这一个结构,前端拿到它就可以直接构造瓦片源, 不必再问后端任何问题。

11交给 OpenSeadragonuseViewer.ts:93

这里就是问题里那个「某个库」:OpenSeadragon,用 canvas 画瓦片。 注意它不是 tileSources: 'xxx.dzi' 那种字符串写法 —— 直接用手上的元数据构造 DziTileSource,省掉一次 .dzi 的 XHR 往返,也绕开相对路径解析。

12这个 URL 谁在接tiles_protocol.rs

bigimgpin://localhost/… 是自己注册的协议,不是文件系统。它只做一件事: 把 URL 路径映射到缓存目录里的一个文件,读出来,带正确的 MIME 和缓存头回给 WebView。 图片字节完全不经过 IPC —— 这是这套架构里最省事的一处设计。

04缓存键与原子落盘

缓存位置:app_local_data_dir()/tiles/<cache_key>/,Windows 上就是

%LOCALAPPDATA%\com.liuliyi.bigimgpin\tiles\
    474a08bb14b2e84b\            ← cache_key，16 位十六进制
        image.dzi
        image_files\{0..16}\…

三件事值得单独点出来:路径 + 大小 + mtime 一起构成「这是不是同一张图」; 切片参数进 hash,所以改参数 = 换目录 = 重切一份; 而 JPEG 质量只在用 JPEG 时才进 hash —— PNG 是无损的,质量参数对它无意义, 否则改一下质量会白白分裂出一份一模一样的缓存（有测试 png_quality_does_not_affect_key 守着这条）。

落盘：临时目录 + 原子改名

防的是什么怎么防的
中途崩溃留下半成品 写在 .tmp-<id>-<pid>/,只有 vips 退出码为 0 才改名成正式目录
改完参数命中旧缓存 参数进 cache_key,目录就换了
只切了 .dzi、瓦片目录没写完 命中判定要求 image.dzi 和 image_files/ 同时存在
清缓存时删到正在写的目录 cache_stats 跳过 .tmp- 前缀;clear_cache 整个根目录删掉
缓存占用为什么给两个数

cache_stats（全局:总字节 + 图片数）和 PreparedImage.cacheBytes（当前这张）是两回事。 只给一个的话,人会拿当前图的大小去估计能清出多少空间 —— 那多半差着几十倍。 状态栏那一格是当前这张,它是清理入口,但不是清理的量。

05瓦片怎么送到前端

WebView 不能直接读 D:\…（也不该读）。这个项目没有用 Tauri 内置的 asset 协议, 而是自己注册了一个 bigimgpin 协议,只暴露缓存根目录:

处理器本身很短:URL → 相对路径 → 白名单校验 → 读文件 → 回响应。

路径校验是白名单，不是黑名单

注册必须用异步版

register_asynchronous_uri_scheme_protocol:同步版的处理器在 macOS 上跑在 主线程,一次慢磁盘 IO 就掉帧。

加一个新命令要同步三处:这里的 generate_handler!、src/api/tauri.ts、src/types.ts。 漏掉第一处,前端调它会直接 reject,而且没有日志告诉你为什么。

06坐标：唯一出口

图像像素 ↔ 屏幕像素的换算全在 src/osd/coords.ts 里,别处不许写第二遍。 文件头列了三条硬规则,每条对应一个真实踩过的坑:

叠加层每帧要转换几十个坐标,逐个调 API 太慢,所以有一个 imageToScreenTransform(viewer):取两个点定出「等比 + 平移」的参数, 之后自己算。无旋转时这个映射就是等比的,两点足够。

坐标小数位：一个设置，三处生效

coordDecimals 默认为 0,也就是全按整数。它同时管: 屏幕上的读数、新框的坐标收敛、导出 CSV 的位数。 拆开管就会出现「屏幕上写 1235、文件里存 1234.57、导出又是 1234.57」, 三处对不上,人就没法信任何一处。

拖手柄：全程在四条边上算

要害是不要对 x 和 w 各自取整 —— 那样原始右边界会被舍入两次,拖左边的时候右边会跟着跳一格。用户拖的是左边,右边一动就说明搞错了对象。

07标注：状态、画布、落盘

一个状态源，撑起撤销

框、辅助线、选中项、撤销栈全在 useAnnotations.ts。 撤销是快照式（整体替换 + 一个 cursor）,不是给每种操作写逆操作 —— 因为「导入整份标注文件」这种一次性替换全部状态的操作,命令式根本接不进去。

由此有四条不能破的规则:

规则为什么
拖拽中只改坐标,松手才 commit() 一次拖拽在撤销栈里是「一步」,不是几十步（setRegionsRects 刻意不记还原点）
自动保存盯 revision,不盯 regions 拖拽每个 pointermove 都换掉数组,盯数组就是一次拖拽触发几十次写盘
叠加层通过 watch(regions) 跟着状态走 漏掉一处 overlay.setRegions() 就是「框进了列表但屏幕上看不见」,只在特定操作顺序下暴露
选中是 Set<string>,不是数组 画布每帧对每个框问一次「你选中了吗」,数组 includes 在框多起来后是每帧几万次比较

画布：自绘一层屏幕空间 SVG

网格、辅助线、框、预览框、八个缩放手柄,全画在一张屏幕空间的 <svg> 上,监听 OSD 的 update-viewport 整层重绘。不这么做的话:线宽会随缩放变成色块 （屏幕空间绘制让线宽恒为 2px）,而且 addOverlay 的坐标系是 viewport 而不是图像。

手柄：画在哪，就在哪命中

drawRegions 画手柄时顺手把八个点的屏幕坐标记进 handlePoints,handleAt(x, y) 直接查那份。 分开各算一次迟早会出现「看着在手柄上、点下去却没反应」,而且只在某些缩放比例下出现。

落盘：源图旁边的 sidecar

标注存在<图名>.bigimgpin.json —— 追加而不是替换扩展名 （a.tif 和 a.png 是两张不同的图,不能共用一份标注）。 同目录写不进去时退回应用数据目录,状态栏显示实际位置。

「半新半旧」是这里唯一的致命坑

image.value = prepared 和 applyAnnotations() 必须在同一个同步块里, 中间不能插 await。否则正在跑的自动保存会读到「新图 + 旧框」这个组合, 把 A 图的框写进 B 图的标注文件。所以读标注拆成了两步: fetchAnnotations（异步、不碰状态）+ applyAnnotations（同步）。

另一条:读不出已有的标注文件时（JSON 坏了、或版本更高）停用自动保存, 而不是报个错接着存。空标注覆盖掉的是用户唯一的产出物。

写盘是串行化的（上一次没写完就记个标记,写完再补一次）,而且刻意不做防抖:

08导出：语义留在前端

export.rs 只管格式化、夹取和写盘。坐标变换不在这层: 要不要套「偏移 / 系数 k」的逆变换,由 RectPanel.vue 决定 —— 它才是持有那套参数的地方。 坐标系语义有两个地方知道,迟早会分叉。

小数位只负责「打印几位」

数值是前端按同一精度收敛好才送过来的。两边各舍入一次会用到两套舍入规则 （JS 的 toFixed 与 Rust 的格式化在恰好 .5 上不一致）, 同一个框在屏幕和表格里就可能不一样。

裁剪：vips 越界会直接不产出文件

09看着像 bug 的故意设计

以下每一条都更像是「漏了一处处理」,但都是故意的。改动前先看一眼理由。

看着像其实是
框能被拖到图像外面 画框时会夹到图内,拖动时不夹 —— 「有时就是要生成越界的框来对照」。真要用到越界坐标的地方（裁剪）自己会夹
拖动模式下没有缩放手柄 那时拖拽是平移画面,画着几个拖不动的方块是骗人
切工具模式没调 setMouseNavEnabled(false) 它会把滚轮缩放一起禁掉。正确开关是 gestureSettingsByDeviceType('mouse').dragToPan
maxImageCacheCount: 80 太小 OSD 默认 200 且不按内存预算,1024 瓦片解码后 4 MB/张,默认值会吃掉 800 MB。视口实际只用约 9 张
drawer: 'canvas' 而不是 webgl webgl drawer 走 XHR,会撞上 range 请求相关的坑,而这个项目完全不需要 WebGL
清缓存要连当前图一起关掉 瓦片文件已经删了,留着图只会是一片空白,而且用户不知道发生了什么。标注不受影响（存在图片旁边）
切片进行中禁用清理按钮 正在写入的目录会被删到一半
改切片参数后旧缓存不自动删 它在磁盘上躺着,要省空间得走「清理」。界面必须把这句因果说出来,否则用户只看到「改了个设置,下次打开图又等了几分钟」
辅助线颜色不跟主题走 它画在图上而不是界面上,判断依据是「在任意图像内容上都能看见」
vips 的进度输出前缀不匹配任何操作名 实际前缀是临时图像名（temp-3）而且会变。有测试用 temp-3 守着,防止有人「修正」成匹配 dzsave
mtime 存进标注文件却不参与「对不上」判断 拷贝文件就会改 mtime,拿它报警只会制造假警报,而被喊几次之后真警报也会被无视
vips 相关测试找不到二进制时跳过而不是失败 开发机上没装 vips 不该让人以为代码坏了
