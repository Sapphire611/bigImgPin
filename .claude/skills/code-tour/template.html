01谁在跑：所有执行体

这一节的作用是先把读者脑子里的错误模型打掉。典型写法:「这是最容易带着 XX 直觉读错的地方。 在 XX 里做这件事是一个进程一次调用,这里不是:同一时刻有 N 个执行体,它们之间靠管道、文件和 HTTP 说话。」

02核心概念（先讲清楚它是什么）

把主链路里最陌生的那个概念先讲明白 —— 否则后面出现的每个术语读者都要停下来猜。 讲的时候给它落在磁盘/内存上到底长什么样,而不是给定义。

反直觉的地方

每个概念都有那个「和直觉相反」的点:索引从 0 开始且最小、坐标系原点在左上、时间是倒着存的…… 单独标出来。

亲手算一遍

凡是文档里出现的「共 N 级 / M 个 / K 张」这类数字,都别硬编码: 用源码里那段公式现算,并让读者能改输入看变化。这样文档自带一次交叉验证。

每行一句话说明方块代表什么、顺序按什么排。公式与 源文件:行号 里的那段一致。

04机制一（缓存 / 状态 / 协议…）

每一节讲一个独立机制,内部结构固定为三段:它解决什么问题 → 关键代码 → 不这么写会怎样。 机制节数量按项目定,3–5 个合适;写不满就把编号删掉,别为了凑数拆开。 代码仍然用 figure + figcaption 标 文件:行号。

防的是什么怎么防的
某个具体的坏情况（崩溃 / 换参数 / 并发）对应的那一行代码或那个判断

05机制二

同样的三段式。适合放「边界与契约」类内容:类型契约、协议、序列化、字段命名。

06机制三

适合放「坐标系 / 单位 / 精度」类内容 —— 这类东西的注释里往往埋着最多坑,原样抄过来。

07机制四

适合放「状态机 / 撤销 / 生命周期」类内容。写清「谁可以改它」,而不只是「它是什么」。

08机制五

适合放「落盘 / 导出 / 持久化」类内容。要点是实际写到哪个文件、什么格式、什么时候写。

09看着像 bug 的故意设计

这一节是整份文档里被引用最多的地方:每一条都更像「漏了一处处理」,但都是故意的。改动前先看一眼理由。

看着像其实是
某处没做校验 / 没夹取 / 没清理为什么是故意的,真要用到的地方谁负责兜
某个参数值明显不合理实测出来的取舍（带上两边各是多少）
那段代码在防一个不可能发生的情况它真的发生过,或者它防的是「静默出错」而不是「报错」
